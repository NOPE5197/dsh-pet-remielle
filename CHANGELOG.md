# Changelog

## [0.4.5] — 2026-10-01

### Changes
- The presentation layer of the bubble session card is extracted into `src/bubble-title.cjs`, shared by both clients (the desktop side is served by the host as `/bubble-title.js`, the web side is bundled into `lib/client.js`): title throttling, the hidden measurement node, box width, deck lift amount, plus the copy, class names and stacked layout for the three approval / plan review / done states. Previously this logic was written out separately in `client.core.js` and `pet-view.html`, so drift such as the "plan review" hint repeating the project name had to be fixed once per client; there is now a single implementation, and the pure functions are asserted directly by `test/bubble-title.test.js`.
- Deck updates and things like the menu/animation are still kept as per-client implementations (the dependency surface differs: the web side handles DSH workspace navigation and approval clicks, the desktop side handles dragging, menus and GIFs).
- The desktop pet's completion reminder is only auto-acknowledged while "a foreground tab is currently looking at that session": hidden tabs do not acknowledge it, and the desktop window being present does not acknowledge it on behalf of a background tab either — it is acknowledged only once the tab becomes visible again. The desktop window itself only shows the reminder and requires an explicit click on the completion card. While a global panel (such as Settings) is open the reminder is kept, and it resumes after the panel closes.
- Test granularity is consolidated: branch cases of the same function are merged into a single table-driven/scenario-based test (`states()`, session-title folding, top-level snapshot fields, deck ordering, overlay wrapping, hang detection, etc.), and not a single assertion was dropped (280 → 221 during the consolidation; further cases were added on this branch afterwards). When maintaining, add tests as "one test per behaviour under test" instead of one per branch.

### Fixes
- **The one-click update and info endpoints previously validated only the Host header and could be triggered cross-origin by any web page**: a cross-origin `POST` with a simple content type does not trigger a preflight, so a malicious page could get the plugin to run `git pull` / `pnpm update --latest` with a one-line `fetch` (pnpm runs dependency packages' lifecycle scripts), and the `info` endpoint even returns the absolute `profileDir` / `repoDir` paths. Both are now uniformly changed to validate a TCP-level loopback address plus same-origin `Origin` and `Host`, the same standard as the guard on endpoints such as `/config`.
- The 10 cases in `test/pet-window-paths.test.js` were not part of `npm test` and had never actually run; they are now wired into the test script.
- **`.gitattributes` gained `lib/client.js text eol=lf`**: this file is a build artifact committed to the repo. Previously it was checked out as CRLF on Windows while the build wrote LF, so every `npm test` run left it permanently showing as modified (`git status` lies while `git diff` is empty). CI also gained a step comparing the committed `lib/client.js` against the current source.
- **The CI test step previously carried `continue-on-error: true`**, so the pass/fail result of the tests was completely invisible on checks; it is now blocking, and the trigger branches have been widened from `main` only to `'**'`.
- **Route registration no longer depends on the optional `connection` service**: the desktop URL fetches the authenticated address on demand and falls back to the local origin when that service is missing or the value is abnormal, avoiding the entire route table silently failing to register.
- **Desktop window exit now finalises per instance**: a late exit by an old Electron process no longer clears the new window's reference; when the web client is already online, the idle bubble also shows an explicit prompt instead of silently swallowing the click.

## [0.4.4] — 2026-09-26

### Fixes
- **Fixed "pet list empty, desktop pet gone" introduced in 0.4.3**: 0.4.3 added a `volatile` marker to the config fields to adapt to DSH 0.1.7, but schemastery also parses already-persisted config values into volatile wrapper objects, and DSH's `settings.get()` and `watch` callbacks return that wrapper as-is — so the plugin's direct property access gets an object rather than a value, emptying the pet registry, falling the usage mode back to ledger, and breaking coordinates/tokens entirely. The register branch of `createSettingsScope` now unwraps uniformly at the `get`/`watch` exits (`readConfig`), and fields that were never persisted fall back to the schema default.
- **The one-click update is no longer wrongly killed by a fixed 90-second hard timeout**: it is now an "idle timeout" — as long as the update process keeps producing output (pnpm's progress lines during download keep resetting the timer, and only 60s of silence counts as hung), with a separate 10-minute overall cap as a backstop. Users on slow networks (especially connecting directly to npmjs inside China) no longer fail with a timeout when upgrading to a version that needs fresh dependency downloads.
- An update process hung past the timeout is now genuinely terminated (together with its child process tree), instead of leaving behind an orphan that keeps rewriting node_modules.

### Changes
- While the update is in progress, the update card **shows the update progress live**: elapsed seconds and the most recent output of the update process (auto-refreshed every second), instead of just one line saying "Updating, do not close DSH".
- When an update fails, the error message is condensed into one sentence (explaining the network cause on a timeout) and now **recommends a manual update**; the update dialog **always keeps a "Manual update (GitHub)" button** (visible in every state — updating / succeeded / failed — placed independently on the left) that takes you straight to the release page. The prompt and the docs no longer expand on details like a manual `pnpm add` / mirror configuration, and the old "View on GitHub" button is merged into it.
- **After a failed one-click update, the integrity of the previous installation is self-checked automatically**: when the update fails or is interrupted by a timeout, the current installation on disk is immediately checked for integrity (pnpm being killed midway can leave a half-finished node_modules), and the failure prompt directly gives the verdict "the old version keeps working normally" or "a manual reinstall is recommended" — the old version is not affected at that moment (the code is already in memory), so users do not have to wait until the next restart to discover the problem.
- All output areas of the update dialog (live output / failure reason / success output) are uniformly height-limited and scrollable (120px), and the release-notes area is limited to 180px, so long logs no longer stretch the dialog to an absurd length.

## [0.4.3] — 2026-09-26

### Fixes
- When plan mode enters the review queue, the desktop pet gains a dedicated "Plan review" state: it shows a summary of the plan title and a bubble hint, it sorts after ordinary approvals and before ordinary questions, and the bubble is only responsible for opening the review — it does not reuse the "Allow once" auto-confirmation.
- With multiple tabs, only the active tab (or the desktop floating window) auto-clears the current session's completion reminder; a background tab no longer overrides the host's current session, nor clears another conversation's completion card ahead of time.
- Adapted to the DSH 0.1.7 volatile settings API: the `SettingsForms.configure()` disposer is now registered correctly, `platformToken` is marked as secret, and `uiWorkspace` becomes an optional service (preferring 0.1.7 workspace navigation, falling back to the old `sessions.open` when absent); the minimum DSH version is not raised.
- Pet IDs gain a format constraint (`PET_ID_RE` moved into the schema); the schemastery dependency is bumped to ^3.18.4.

## [0.4.2] — 2026-09-21

### Changes
- The "Appearance" tab in the settings is rearranged: "Mirror horizontally" moves from the very top to below "Opacity", so the Appearance page is now ordered "Character size → bubble zoom (with sub-items) → Opacity → Mirror horizontally" — sliders of the same kind (size / opacity) cluster together, and the mirror switch closes the list. The right-click menu order is unchanged.
- The release notes in the update card and in the settings "About" page are now **rendered as markdown**: the GitHub release body is markdown, but it used to be stuffed into a `<pre>` as plain text, so headings / lists / links / code all ran together into a single line. There is now a good-enough subset renderer (headings, ordered / unordered lists, fenced code blocks and inline code, blockquotes, horizontal rules, bold / italic / strikethrough, links), paired with `.rm2-md` typography classes (a semi-transparent overlay colour that works in both themes, with a slight tweak to the code background in dark mode). Safety convention: escape everything as HTML first and then apply the markdown transforms, and only allow http(s) / mailto links (everything else becomes `#`) — the release body comes from a remote host and cannot be trusted. Update output and failure reasons are still process logs: they stay monospace and verbatim, and take no part in markdown parsing. The guardrails gained a source-level assertion plus behaviour unit tests for the renderer, keyed by slice markers (XSS escaping, link protocol allowlist, list / heading / code-block parsing).
- Renaming is now entered by **double-clicking the pet's name**: previously there was a standalone "Rename" button that took up space and hid the entry point; now the name itself is the entry point (with a "double-click to rename" hover hint), and the editing state is an input plus save (Enter saves, Esc cancels, blur auto-saves). Pets whose directory is missing keep a plain-text name (a rename request against a non-existent directory can only fail). Source-level and render-level assertions now pin down that "the double-click entry exists and the standalone rename button must not come back".
- Fixed the settings page's primary button being **unreadable with black text on a black background**: the primary button text originally used `--dsw-alias-brand-primary-invert`, but measured against the DSH host theme definition, in the light theme that variable has the **same value** as `brand-primary` (both a near-black #0f1115) — the accent is near-black and so is its inverse, so save / one-click update / add-and-enable all collide. DSH's light-theme accent is near-black and its dark-theme accent is near-white (not the blue #526aa8 we had assumed), so `--dsw-alias-bg-layer-1` — naturally the inverse of the theme accent (light #fff / dark #232324) — is used as the text colour, which is then correct in both themes automatically; hover is changed to an opacity change instead (`button-primary-hover`'s values in the two themes relate unreliably to the background colour). The guardrails gained a source-level assertion: `.rm2-pet-btn-primary` must not use `brand-primary-invert` as its text colour. Mutation testing confirms 5/5 that each assertion bites.
- Fixed the settings page's primary button showing **white text on a light background on hover**: the primary button element also carries the `.rm2-pet-btn` class, and after the previous change made hover an opacity change, `.rm2-pet-btn:hover:not(:disabled)` (specificity 0,3,0) still outweighs `.rm2-pet-btn-primary` (0,1,0), replacing the hover background from the near-black accent with light grey `--dsw-alias-interactive-bg-hover` while the text stays white → the colours collide the moment the mouse lands on it. The primary button's hover now explicitly writes the `brand-primary` background back at the same specificity (winning on source order coming later), so hover only fades the opacity and leaves the background alone; the guardrails gained a "hover must write back the primary background" assertion, mutation testing 6/6.
- The settings-page controls are aligned with the host UI style: the rename-related controls had no styling at all — the "Rename" and "Save" buttons and the editing-state input were all the browser's native default look (grey system buttons), inconsistent with "Set as current" on the same row (hand-written inline styles) and nothing like DSH's native controls. The root cause is that this whole section of the settings mixed in a batch of **CSS variables that do not exist** (`--border-color` / `--danger-color` / `--surface-color`; DSH's vocabulary is `--dsw-alias-*`), so they always fell through to the light fallback and the border/error colours were all in the light family under the dark theme; and inline styles cannot express `:hover`, so no button had any hover feedback. Going through the plugin's existing `<style>` injection mechanism, three base classes are added: `.rm2-pet-btn` (ghost button, with hover/disabled states), `.rm2-pet-btn-primary` (primary button) and `.rm2-pet-input` (input, with placeholder/focus states), using only DSH's native `--dsw-alias-*` variables — light/dark switches automatically through the host variables, so dark-mode overrides are no longer needed. Every settings-page button (set as current / retry / reset position / check for updates / update now / feedback ×2 / dialog close) and input (rename editing state / platform token / add pet ×2) is switched over uniformly; the three ghost variables such as `--border-color` are fully replaced with real variables (`--dsw-alias-border-l2` / `--dsw-alias-label-error` / `--dsw-alias-bg-layer-*`), and the section root style drops the forced `font-family` in favour of inheriting the host font.
- The settings page's "Pet Management" is split out into its own tab and the lost features are wired back: the pet registry (list / rename / set as current / enable switch / add pet) used to be crammed at the bottom of the "Appearance" tab, semantically unrelated to the appearance items (mirror / size / opacity); it is now a standalone "Pets" tab, and the section title and the left-hand navigation are unified as "Pet Management" (previously the navigation said "Pet Management", the page you landed on said "Desktop Pet Settings", and the tab itself had yet another group with the same name — three places fighting each other). At the same time, two features that previously existed only in dead code are wired back up: **pet renaming** (`RenameButton`) and the **status badge** (`petBadge`: enabled / disabled / directory missing / missing images, 01–06 must all be present) — when a pet's directory is missing or images are absent, the enable switch used to just silently grey out and users had no way to learn the reason; the reason is now shown directly on the card. The dead `petCard` (~50 lines, a second implementation of the pet card that was never called) is deleted, and the thumbnail now uses the registry's `previewMood` (a pet with missing images no longer always requests 06.gif and ends up with a broken image).
- Checking for updates now gives visible feedback when it hits "the repository has never published a release": previously the `no-release` state had no branch in the render, so clicking "Check for updates" looked like nothing had happened. A new settings-structure guardrail `test/settings-section.test.js` (a fake React drives `PetsSection` directly) was added at the same time: it pins the tab list and order, that the title and the navigation agree, that the pet card's rename button and status badge must render, that `no-release` must have visible copy, and that `petCard` must not come back — mutation testing confirms 5/5 that each assertion bites.
- The right-click menu is unified across both clients: previously the web side only had "Pause animation / Reset position / Desktop floating mode" and the desktop side only had "Draw / Usage mode / Switch to web mode", and the same `desktopMode` setting carried two different names on the two clients. Both clients now share one skeleton, one order and one set of names — status info · character size · opacity · mirror horizontally · lock position · pause animation · show bubble · draw · reset position · desktop floating mode. There are three inclusion criteria: it must be visible on the pet immediately after clicking, you should not have to jump to the settings page for it, and turning it off must still leave a way back; by that measure, enable/hide desktop pet, Pet Management, respond to sub-agents, usage mode and the platform token, and the bubble sub-items and fine-grained bubble scaling options all stay in the settings page only (the desktop menu's "Usage mode" is removed and merged into the settings entry). `desktop-window` gains an assertion pinning that the item sets of the two clients are equal, so adding or removing an item on either side turns the build red.
- The right-click menu is completed with "Opacity" (a 0.3–1 slider) and "Mirror horizontally", and "Draw" is added to the web menu (sharing one entry point with double-click; the web `playDraw` is extracted from the double-click handler).
- The right-click menu is narrowed and its sliders tidied up: the menu width used to be determined by its content (`min-width:200px` plus the length of the status-row copy; measured at about 280px), and it is now a fixed 240px with row spacing 18→6px and row padding `7px 10px`→`7px 9px`. The slider row becomes "label column `flex:1` + fixed-width slider 92px + fixed-width percentage 36px": the label column absorbs the slack so the slider is pushed to the end of the row, and the left and right edges of the sliders in the "Character size" and "Opacity" rows line up exactly (with the old markup the two rows had different label lengths, and `space-between` placed them differently — measured in real Chromium, the old geometry gave label columns of 52px / 50px and the sliders were misaligned by 2px; the new geometry gives 64px for both, so the slider rectangles are identical). The slider size and the percentage column are no longer written into inline styles in JS (a separate copy on each client is guaranteed to drift); `desktop-window` gains two assertions pinning that "the geometry parameters of both clients are equal item by item" and "the label column is wide enough for the longest slider label".
- The cross-client menu consistency guardrail is upgraded: previously it only asserted "the item sets are equal"; it now also pins the **item order** and the **config key each item writes back** (items with the same name must change the same config), with the write target of each key item spelled out. Such "only changed on one side" bugs used to pass silently (`desktop-window`'s assertion only checked the set). Mutation testing verifies that the two new assertions really do turn red (swapping two items in the order on either client, and rewriting the desktop side's "Mirror horizontally" to a different config key, each trigger the corresponding failure). Leftovers on the desktop side are cleared at the same time: the `.menu select` styling left behind by the removed "Usage mode" dropdown (including its dark adaptation) goes away with it.
- The two clients now share one theme source and the colours no longer fight: the desktop floating window used to follow the **system** light/dark setting (`prefers-color-scheme`) while the in-page pet followed the **host** theme (`body[data-ds-dark-theme]`) — with combinations such as "system dark + DSH light theme", the same menu is two different colours on the two clients (items, order and geometry still match item by item; only the palette is inverted). The web client now reports the host theme to the host (`POST /theme`, watching additions and removals of `data-ds-dark-theme` on `body`, plus a 5-minute heartbeat renewal), the snapshot carries a new `hostTheme` field, and the desktop window folds "host report > system preference" into a single `html[data-host-theme]` attribute that drives the palette; when no web client is online or the report has expired (10-minute TTL on the host side) it falls back to the system theme. The desktop dark rules therefore no longer use `@media (prefers-color-scheme: dark)`: when a media query and the attribute both match, the winner depends on source order, so keeping both rule sets amounts to rolling dice with rule order for the palette.
- A cross-file consistency guardrail is added for the dark palette on both clients: after normalising the rules on both sides (stripping the host prefix and the web-specific `rm2-pet-` class prefix, removing whitespace) the colour values are compared rule by rule, and among the 11 same-named rules only one known intentional difference is allowed ("solid shell vs .96 semi-transparent" — under the desktop window is the real desktop, and a semi-transparent shell would let the wallpaper's pink tint bleed through). Supporting verification: real Chromium rendering confirms that the attribute really does drive the palette (`dark` → menu `rgb(72,20,42)` / `#ffd6e4`, `light` → `rgb(255,240,245)` / `#8a2f52`), reproducible via `.global_ignored/theme-parity-probe.mjs`; mutation testing confirms that four kinds of breakage — transcribing a colour value wrong by a single character, dropping the snapshot consumption, reverting the dark rules to a media query, and reversing the fold priority — all turn red.

### Fixes
- The desktop window's userData directory is moved out of `%TEMP%` and given an exclusive lock (added in issue #21): the original implementation put Electron's userData in `%TEMP%/dsh-pet-remielle`, which system disk cleanup deletes wholesale (taking the Electron cache and the renderer layer's position fallback with it); it also cannot switch to the host's default `%APPDATA%/Electron` — sharing one profile locks the disk cache and serves stale responses (a historic bug: the page kept running old right-click logic that had been deleted). It now uses a stable directory (Windows `%APPDATA%\dsh-pet-remielle`; macOS / Linux use their own application-data directories) and maintains a `pet-window.lock` there recording the occupying pid: when the stable directory is taken by **another live instance** (the host-exit watchdog has a delay, so restarting the host quickly makes the old and new windows overlap) it backs off to a `<dir>-<pid>` sibling directory, avoiding two processes sharing one Chromium profile and reintroducing stale caches. The lock is only written, and only deleted, when you are its rightful owner, so a lock left behind by a crash is judged idle at the next startup because its pid is dead (self-healing). The host watchdog's polling interval is also reduced from 3000ms to 1000ms — after the host exits the desktop window lingers at most 1 second, which also squeezes the old/new instance overlap window down to within 1 second. The decision and the lock read/write are extracted into `src/pet-window-paths.cjs` (pure logic, with 10 unit tests covering self-healing / backoff / garbage values / ownership checks, including the criterion that "EPERM must be treated as alive"). Verified on real hardware with an actual Electron main process: the stable directory `…\AppData\Roaming\dsh-pet-remielle`, a full lock write—read—release round trip, and `app.setPath` reading back consistently. Upgrade impact: the old `%TEMP%/dsh-pet-remielle` stays on disk and can be deleted manually; the window coordinates themselves are persisted through the host config and are unaffected.
- The row height of the right-click menu's toggle rows jitters when ticked: the check mark "✓" (U+2713) falls back to a different font on this machine, and its glyph box is **19px** tall while the label is only 16px, so under `line-height:normal` the row's line box is stretched from 30px to 33px — every tick makes the whole row (and with it the overall menu height) jitter by 3px. `.tick` now gets `line-height:1` to suppress the check mark's own contribution to the line height (synced on both clients; measured, the tick box goes 19→13px, the row height stays constant at 30px, the tick's vertical centre offset is 0, and its visual position is unchanged). The desktop dark branch may now only override colour and must not write line height again — otherwise light mode looks fine while dark mode still jitters. Measured in real Chromium (reproducible via `.global_ignored/menu-row-height-probe.mjs`): before the fix both clients' row heights were `[30,30,30,33,30]`, after it `[30,30,30,30,30]`; mutation testing confirms that four kinds of breakage — omitting `line-height` on either client, pushing the line height into the dark branch, changing the font weight inconsistently on the two clients, and restoring the old insertion condition — all turn red.
- The DOM structure of the toggle rows is inconsistent between the two clients (the label column differs by 6px): the desktop `menuRow` used to test `value !== null && value !== undefined`, inserting an **empty** tick span even when unticked, and an empty span still occupies a `gap` slot in a flex layout → the label column of the desktop client's five rows "Mirror horizontally / Lock position / Pause animation / Show bubble / Desktop floating mode" was 6px narrower than the web client's (the web `makeRow` uses a truthiness test and inserts no span when unticked). Both clients are now uniformly "insert only when on", and `desktop-window` gains a "the check mark must not change the row height" assertion pinning that the rules on the two clients are equal item by item, that the dark branch writes no geometry, and that the insertion conditions match.
- The desktop dark bubble is missing a `color` fallback: the web `body[data-ds-dark-theme] .rm2-pet-bubble` has always carried `color:#ffd6e4`, while the desktop side only has `background` and `border-color`, so the bubble body's text colour stays the inherited black in dark mode (the title and the detail each carry their own colour, so it only shows up when new text nodes are added or the styling is split out on its own). It is now aligned with the web client item by item; the bubble text colour in dark mode measures `rgb(255,214,228)`.
- After the right-click menu was narrowed to 240px, "Character size" was rendered as "Characte…": the slider row's label column carried `min-width:0` plus `text-overflow:ellipsis`, and the space left for the label column in a fixed 240px menu sat exactly on the threshold for four CJK glyphs (about 52px) — a slightly wider CJK font metric was enough to trigger the ellipsis. That space is now given back to the label column (slider 100→92px, percentage 38→36px, row spacing 8→6px, label column usable 52→64px), and **shrink plus ellipsis is cancelled for interactive rows**: if the menu gets narrower again it becomes a visible overflow rather than silently swallowing the title. Truncation is kept only for the status row (`.rm2-pet-menu-status` / `.menu-status`) — the web status row is simultaneously changed to a **single** span structurally matching the desktop one (the whole string "mood · message · running"); when it was split into two spans a long message could not shrink and simply overflowed the menu's rounded corners.
- "Pause animation" stopped on the first frame instead of the current one: `canvas.drawImage(<img src=animated GIF>)` in Chromium always paints only the first frame (measured locally with a 360×360 / 120-frame sticker: 20 samples over 462ms covering 7 full loops had pixel signatures that were completely identical and equal to frame 0), so the old implementation snapped the pet back to its starting pose the moment you paused. A shared `src/gif-frame.cjs` was added for both clients (the desktop side is served by the host as `/gif-frame.js`, the web side is bundled into `lib/client.js`): read the GIF's per-frame durations → locate the frame number from the "milliseconds already played" → decode that frame with the WebCodecs `ImageDecoder` and swap it in. Hovering the menu item pre-warms the frame table (120–160 frames takes about 0.1–0.4s), so clicking freezes immediately. `ImageDecoder` requires a secure context (`127.0.0.1` / `localhost` / https count; a plain-HTTP LAN address does not) and falls back to the original first-frame snapshot when unavailable; the pause toggle itself is unaffected. The frame-number computation is a pure function (`test/gif-frame.test.js`), and the frame-retrieval chain has a separate real-Chromium end-to-end script verifying that "the computed frame number == the actually decoded frame" (`.global_ignored/electron-gif-freeze-probe.cjs`, 22/22 exact hits including loop wrap-around). **Known boundary**: unpausing reassigns `img.src`, and the browser replays the GIF from frame 0 instead of resuming from the frozen frame.
- Right-clicking while the sticker is still decoding silently fails to open the menu: the `img` height is 0, `menuBoxOf` judges it empty, and `pickMenuPos` then hands `null` to `sideMenuPos`, which reads `r.right`, throws a `TypeError` and aborts menu positioning — on the desktop this shows as the menu staying at the offscreen measurement position `-9999px` (right-click looks like a no-op), and on the web as staying at the old coordinates. Both clients' `sideMenuPos` now anchor an empty box to the bottom-right of the viewport (which is where the pet sits anyway).
- The web client's right-click "Pause animation" looked like it did nothing when clicked: it only changed local state and never wrote the config, while `applySnapshot` corrects the local state from `config.paused` on every pass — so the next snapshot flipped it back. It now writes the config instead; the desktop client gains the same toggle (previously you could only pause from the settings page).
- The settings page's "Reset position" button launched the desktop floating window instead: the button was mistakenly wired to `POST /desktop/start`. It now has the same semantics as in the right-click menu, clearing all four coordinates in one go.
- "Reset position" only cleared the in-page coordinates (`posX`/`posY`) — the desktop window's coordinates live in `desktopX`/`desktopY`, neither client had a reset entry point, and in desktop mode dragging the pet off-screen left it unrecoverable. All four coordinates are now cleared at once; the desktop reset also clears the renderer's `localStorage` fallback snapshot (otherwise the next launch `moveTo`s the window with the stale snapshot and silently undoes the reset) and invalidates `menuBase` (clicking this item while the menu is open makes the subsequent `closeMenu → menu-restore` move the window back to its pre-reset position).
- The settings page's "Hide desktop pet" hint says "wake it from the right-click menu or the status bar", but that item has never existed in the right-click menu — the copy did not match the implementation.
- The period hint (off-peak/peak) lagged behind DeepSeek's official rule (issue #25): the decision previously looked only at the hour, so weekends and Chinese statutory holidays were also judged peak. The current official wording is "peak on weekdays 9:00–12:00 and 14:00–18:00 (Beijing time); Saturdays and Sundays are off-peak all day (since 2026-08-23); statutory holidays are off-peak all day; and weekends that are make-up workdays are also off-peak all day" — the latter two make the make-up-workday information redundant, so the decision only needs "weekend ∪ statutory holiday". A new `src/holidays.js` is added: a built-in 2025/2026 holiday calendar as a fallback, with silent background refresh of public holiday data cached at `$DSH_HOME/.dshp-holidays-<year>.json` (30-day TTL; an empty result for an as-yet-unpublished year gets a 3-day TTL), falling back silently on failure. Years not in the table fall back to a fixed-date approximation (New Year's Day / Labour Day / National Day), guaranteeing no false peak readings on known fixed holidays. `isPeakTime` in `balance.js` is accordingly changed to a "weekend/holiday + hour" decision, and the previously entirely missing test coverage is added.
- The Electron runtime fails to install inside an Electron host (DSH Desktop) and cannot self-heal (issue #24): the host patches `node:fs` for ASAR, and during the per-file copy reading `resources/default_app.asar` itself is misjudged as an in-archive path and ENOENTs; furthermore `electron.exe` has already copied successfully and the integrity check only looks at the exe, so a half-finished install is treated as installed. win32/linux now use "staging extraction → integrity check of the key files → atomic publish by directory rename" (renaming does not read file contents, so it naturally sidesteps the ASAR patch; if the rename fails it falls back to the ASAR-safe `original-fs` copy), with a new unified integrity check `isUsableElectronRoot` (exe + default_app.asar + pak/snapshot, non-empty regular files). Both the fast path and candidate discovery validate this way, and exe-only leftovers are automatically cleaned up and reinstalled.
- With desktop mode enabled under DSH Desktop the pet disappears and the window shows `forbidden`: DSH Desktop wraps every WebServer route (including this plugin's endpoints) in a `desktopBrowserAccess` renderer admission check, and unless "browser access" is enabled only requests carrying a dedicated header pass, so every request from the standalone pet's Electron window gets a 403. The plugin now reads the renderer admission header from the host context and passes it via env to the pet window process, which self-injects it into same-origin requests before creating the window (the same mechanism DSH Desktop's own renderer uses); an ordinary web host has no such service, so behaviour is unchanged.
- When the Electron runtime is incomplete (exe present, key files missing) the download confirmation dialog pops up over and over but a download can never start: ① the web download dialog is not reset after the previous run's done/error — when it pops up again the "Start download" button is already hidden and only "Close" remains, so the user cannot start a download; ② the `/desktop/cancel-download` endpoint falls through to a second `jsonResponse` at the end after responding, and the host log repeatedly warns `ERR_HTTP_HEADERS_SENT`. Both the dialog reset and the double response are fixed. Hardening included: the runtime integrity check is immune to the ASAR-patched fs (when `stat` is untrustworthy it falls back to the real parent directory listing to decide existence); the pet window watchdog correctly treats `kill(pid,0)`'s EPERM (the process is still alive) as "host alive" and no longer kills it wrongly; and both the window-exit and "no backend" missing-file lists are written to the host log to ease troubleshooting.
